# Zepit — Project Handoff Doc
## 1\. What this is

A hackathon project for **The Zerops Challenge** (WeMakeDevs). Working name: **Zepit**. It's a tool that takes a plain-English app description, matches it to one of a few pre-built application archetypes, provisions the matching multi-service infrastructure on Zerops, deploys already-written code, and hands back a live, working URL. The end user does **not** write any code — the deployed app is functional out of the box (this is "option 1," decided deliberately over the alternative "scaffold-then-user-codes" model).

## 2\. Hackathon facts & rules that constrain the design
- **Event:** The Zerops Challenge, online, **Aug 8–9, 2026** (48 hrs). **Solo only**, one project each. (Account shown as already registered.)
- **Prizes:** MacBook Neo (best overall), Logitech MX Master 3 (best social post), $5,000 Zerops credits pool.
- **Hard requirements:** project must be **deployed and running on Zerops**; Zerops must be **meaningfully used**; judges must be able to open a **live URL** that **stays up through judging**; source must be **readable** (public repo or private shared with judges).
- **Complexity bar:** "Hello World" disqualifies. Aim for **≥3 services** (frontend + backend + database is the stated shape).
- **Submission needs:** live URL, source access, **demo video**, explanation of how Zerops is used, plus a **public build post tagging @WeMakeDevs and @zeropsio**, and the **official submission form** (the social post alone is not a submission).
- **AI policy (important for this project):** AI may help you build; **disclose all AI tools** in the form; a project generated **entirely** by AI with no meaningful original work is rejected; you must **understand your code and explain the architecture/decisions** to judges.
- **Head start allowed:** planning, architecture, setting up the Zerops project, and building before the event is fine — you just can't submit something already finished before it began.
## 3\. Why Zepit fits the rules

It maps directly onto the hackathon's own suggested **"Zerops tools"** category ("a zerops.yaml generator, deployment analyser, migration assistant, or architecture visualiser"). The tool itself must also be deployed on Zerops as a 3-service app in its own right — that satisfies the deployment/complexity rules independently of whatever it provisions.

## 4\. Relationship to ZCP (so you can explain it to judges)

**ZCP = Zerops Control Plane**: an MCP server exposing one project's live state and controls to a general-purpose coding agent (Claude Code, Codex, Antigravity, Grok Build), which can read logs, write arbitrary code, deploy, verify, and loop on failures. Zepit is **not** ZCP and does **not** use a coding agent at runtime. The clean one-liner for judges: *"ZCP lets an AI write arbitrary code into a live project; Zepit picks one of my pre-built templates and fills a few fields — no code is generated at runtime."*

## 5\. The AI's actual job (narrow, on purpose)

At runtime there is **one structured LLM call** that does **classification + parameter-filling only** — it never writes code. It receives the user query (+ optional constrained stack picks) plus a catalog of archetype manifests, and returns strict JSON like `{ archetype, fields }`, constrained via structured-output/JSON-schema mode. The application code for each archetype is **written by you ahead of time** (AI assistance while building is fine and must be disclosed). Personalization happens through **environment variables**, not by rewriting source per request.

## 6\. Architecture — two layers

**Layer 1: Zepit itself** (your submission), a 3-service app deployed on Zerops:

- **Frontend** — the form/chat UI collecting the query (+ optional stack picks).
- **Backend** — Express (or similar) holding orchestration: LLM call, archetype matching, template filling, shelling out to zcli, polling, health-checking. Holds the Zerops **Personal Access Token** as a secret env var. (Demo caveat to disclose: single demo credential, not multi-tenant auth.)
- **Postgres** — job table: query text, chosen archetype, filled YAML, status (queued→provisioning→building→live/failed), target project ID, live URL, timestamps. Optionally Valkey or simple DB-row polling for async jobs.

**Layer 2: the target deployments** Zepit provisions per request — a fresh Zerops project per archetype, services wired by private-network hostname, only frontend/API exposed publicly via subdomain.

## 7\. The runtime pipeline (identical for every archetype)
1. Frontend submits query → backend creates job row (`queued`).
2. **One LLM call** → returns `{ archetype, fields }` as validated JSON.
3. **Server-side validation** against the archetype's manifest schema; on failure, fallback (e.g. substitute nearest supported option, or ask user to re-pick).
4. **Template fill**: substitute fields into `import.template.yaml` (string templating only — no source edits).
5. `zcli project project-import <file> --org-id <org>` → creates project + services (`provisioning`).
6. `zcli service push --project-id <id> --service-id <id> --working-dir <template/serviceFolder>` for each runtime service → builds & deploys the pre-written code (`building`).
7. **Poll then verify**: poll pipeline until success, then **health-check the live URL for real behavior** (not just a 200) before flipping to `live` and returning the URL. Frontend polls job status and shows the link.

**Golden rule:** never report a URL until a real behavior check passes ("proof or a blocker").

## 8\. Template structure (per archetype)

```
templates/
 realtime-chat/
 manifest.json # catalog entry: id, description, services, fillable fields (+enums/limits)
 import.template.yaml # Import YAML skeleton with {{placeholders}}
 api/
 server.js # finished code; reads personalization from env vars
 package.json
 zerops.yaml # static build/run recipe
 frontend/
 index.html
```

Manifest example:

json

```json
{ "id": "realtime-chat",
 "description": "Chat app with rooms: Express + WebSockets + Postgres.",
 "services": ["frontend","api","db"],
 "fields": {
 "appTitle": {"type":"string","maxLength":40},
 "roomName": {"type":"string","maxLength":30,"default":"general"},
 "theme": {"type":"enum","values":["light","dark"]}
 } }
```

Design rule: **keep permutations low** — don't make DB type a free field; make each DB/stack variant its own archetype. Personalize via env vars injected in the import YAML, so the **same tested source is pushed every time**.

## 9\. Two worked examples

**A. Realtime chat** ("Express + WebSockets"): archetype `realtime-chat`, 3 services (frontend static + api nodejs@22 + db postgresql). WebSockets need **no special config** — one port with `httpSupport: true`; the `ws` library rides the same Node http.Server. Verification step: open a test WebSocket and confirm the upgrade handshake, not just the homepage.

**B. Image processing** ("upload image → resized thumbnail"): archetype `image-processing`, 5 services — frontend (static) + api (nodejs) + worker (nodejs, private, no public access) + queue (valkey) + db (postgresql) + storage (object-storage). Two `service push` calls (api and worker are separate codebases). Verification step: upload a test image, wait for the worker to process, confirm a resized file lands in object storage.

Only the **manifest + template folder + per-archetype health check** differ; the whole pipeline is otherwise identical.

## 10\. Key Zerops technical facts learned
- **Two YAML files, don't conflate:** *Import YAML* = infra-as-code (creates project + services; run via `zcli project project-import` / `service-import`). *zerops.yaml* = one service's build/deploy/run recipe, lives in the service repo (can also be embedded in import YAML via `zeropsYaml`).
- **No managed MongoDB on Zerops.** Available managed DBs: PostgreSQL, MariaDB, KeyDB, Valkey, Qdrant, Elasticsearch, Meilisearch, Typesense, Kafka, NATS, object-storage, shared-storage. → If a user asks for Mongo, either exclude it from the picker or map to Postgres and tell the user.
- **Service type strings:** `nodejs@22`, `postgresql:single@16` / `postgresql:ha@16`, `valkey@7.2`, `static`, `object-storage`, etc.
- **Hostname rules:** lowercase a–z / 0–9 only, **max 25 chars**, unique per project (slugify generated names).
- **Ports (zerops.yaml):** `ports: [{ port: 3000, httpSupport: true }]`; port must be 10–65435; `httpSupport: true` marks a web server / enables public access config.
- **Public access:** [CORRECTED 2026-08-06 — see PIPELINE.md] `enableSubdomainAccess: true` in import YAML **did not take effect**, and cannot be enabled until after a service's first successful deploy. Always call `zcli service enable-subdomain` explicitly, post-push. Original note: `enableSubdomainAccess: true` in import YAML (or `zcli service enable-subdomain`). Private services just talk by hostname on the project's private network.
- **Deploy is async** — must poll. Useful zcli: `login <token>`, `project project-import`, `project service-import`, `service push` (builds+deploys, the recommended way), `service deploy`, `service enable-subdomain`, `service log --follow --show-build-logs`, `service list`, `project create/delete`.
- **Secrets/personalization:** [CORRECTED 2026-08-06 — see PIPELINE.md] `envVariables` is **NOT** a valid service-level key in an import YAML — it is silently ignored and caused a 502; use `envSecrets`. `envVariables` only works inside `zerops.yaml` under `build:`/`run:`. Original note: `envVariables`, `envSecrets`, `dotEnvSecrets` in import YAML; `<@generateRandomString(<32>)>` needs `yamlPreprocessor` enabled.
- **buildFromGit** works but the repo must be **public** and URL must have **no trailing `.git`**. We chose `zcli service push` from local folders instead, to avoid a GitHub dependency.
## 11\. Decisions locked

- Narrow LLM job (classify + fill only), constrained structured output, server-side validation with fallback.
- Fixed small menu of pre-tested archetypes; personalization via env vars, not source templating.

- Poll-then-verify before returning any URL; per-archetype behavior health checks.
